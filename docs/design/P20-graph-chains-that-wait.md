# P20.01 · Graph chains that wait

2026-11-07, design note for Phase 20, **approved by the owner 2026-11-07** (all four recommended answers) (`docs/ENGINE-CHECKLIST.md`).
The questions at the end were the parts the owner decided.

## What exists today

- The Logic Graph (`tools/AgbStudio.Scripting/Graph`) turns each event node into a plain C# method of a `Behaviour`:
  `Start`, `Update`, `LateUpdate`, `OnTouch(Actor other)`, `OnDestroy`, and one `OnButton<Key>` per button. Every
  node is one statement; nothing can wait. C# goes back to a graph only for files the graph wrote (D-11).
- Waiting lives in `[Cutscene] async Task` methods (P6.10 to P6.13). They compile to Event Script bytecode, not C++,
  and can `await` `Say`, `Choice`, `Move`, `Wait`, `WaitUntil`, `FadeIn`, `FadeOut`. Calling one from normal code
  starts it in the VM; a cutscene in a `Behaviour` gets its actor as `actor`.
- Bytecode can do less than C++: its own `int` / `bool` / `fixed` / enum variables, `Game` fields, Story / Flags,
  `if` / `while` / `for` / `switch`, and calls that have a `[ScriptOp]` or `[ScriptNative]`. It cannot read input,
  physics bodies, an `Actor` other than `actor` / `Player`, or call most of the API.
- Every started cutscene runs at `Priority::Cutscene` (`ProjectApi.agb_start_script`). While any context of that
  priority runs, `Input.*` reads nothing, the player behaviour stops, scene connections do not fire and the pause menu
  is closed (`script::cutsceneRunning()`). The VM has 8 contexts, 16 variables and 24 stack entries per script.
- `OnTouch` runs every frame two actors overlap (`actor.cpp`), not once when they meet.

## The shape: the chain splits at its first wait

A chain runs as today until the first node that waits (Choice waits too). From that node on, the rest of the chain
becomes a `[Cutscene] async Task` method of the same class, and the event method ends by starting it. Nodes before the
split keep everything they can do today, so a chain can read input or a physics value first and wait afterwards.

A Branch or Compare Tag before the first wait stays in the event method, and each of its chains splits on its own
(`OnButtonAWaits` in `GraphWaitTests`). The condition is read when the event fires, so it may read input or physics.
(Changed while building, 2026-11-07: the first draft moved the whole Branch into the cutscene, which would have
forbidden input and physics in its condition.)

Graph: On Touch (Tag Player) → Play Sound "door" → Say "shop.hello" → Choice ("shop.buy", "shop.leave")
→ option 1: Add to Variable coins −5 → Say "shop.thanks"; option 2: Fade Out 0.5 → Load Scene "Town".

```csharp
// Generated by AGB Studio Logic Graph from Shopkeeper.graph. ...
using GBA;
using System.Threading.Tasks;

public class Shopkeeper : Behaviour
{
    void OnTouch(Actor other)
    {
        if (other.tag != "Player") return;
        Sound.Play("door");
        OnTouchWaits();
    }

    [Cutscene]
    async Task OnTouchWaits()
    {
        await Say("shop.hello");
        var choice1 = await Choice("shop.buy", "shop.leave");
        if (choice1 == 0)
        {
            Game.coins += -5;
            await Say("shop.thanks");
        }
        else if (choice1 == 1)
        {
            await FadeOut(0.5);
            Scene.Load("Town");
        }
    }
}
```

- **Name:** the event method's name plus `Waits` (`StartWaits`, `OnTouchWaits`, `OnButtonAWaits`). Two event nodes
  of the same kind share one method today; each chain that waits gets its own, numbered from the second
  (`OnTouchWaits2`).
- **Choice:** one exec output per option. The result goes into `choiceN` and an `if` / `else if` per connected
  option; options with nothing connected get no `if`. `N` counts Choice nodes in the method, so nested choices do
  not clash.
- **Back to a graph (P20.03):** `GraphFromCode` accepts the `using System.Threading.Tasks;` line, the trailing call to
  a `...Waits` method of the same class as "the chain continues there", `await X(...)` as the new nodes, and
  `var choiceN = await Choice(...)` followed by its `if` chain as a Choice node. Anything else in a cutscene method is
  still "not a generated graph", as today.
- **Graph file:** stays format 1. The new node types are only new `type` names; an older AGB Studio shows them as
  unknown, the same as any node added since.

## Which nodes can sit after the split

Only nodes whose C# compiles to bytecode. `GraphChecks` names any other node (P20.05): the Logic Graph draws it with
a red border and puts the reason in the inspector, and the build stops with the same words (AGB0303), for example
"Set Velocity X can't run after a wait: the waiting part runs as a cutscene, which can't do that. Move it before the
first wait.".

| Allowed after the split | Not allowed after the split |
|---|---|
| Wait, Say, Choice, Move, Fade In, Fade Out (new) | Set Velocity X / Y, Set Velocity, Add Force, Jump |
| Play Sound, Play Music, Stop Music, Shake Camera | Is On Ground, Velocity X / Y, Get Velocity |
| Set Variable, Add to Variable, Get Variable | Button Pressed / Held / Released, Axis X / Y, Any Key |
| Save Game, Load Game, Checkpoint, Show Text, Debug Log, Load Scene | Destroy, Camera Follow, Set Tile, Compare Tag |
| Branch, AND, OR, NOT, Add, Subtract, Multiply, Compare, Random Range | Save Exists, the `other` pin of On Touch |
| Move's own Self / Player setting | Self, and every value node not in the left column |

Two of the "not allowed" rows are only missing a `[ScriptOp]` (Save Exists, Set Tile). Adding one is a runtime
native plus a test; they can follow later without changing this design.

**Events that cannot wait:** On Update and On Late Update (they run every frame: a wait would start a new copy each
frame) and On Destroy (the actor is gone). A waiting node reachable from them is an error on the node.

## How values are read

A value is read when its node runs, not when the event fired. `Get Variable coins` after `Wait 60` reads coins one
second later; `Random Range` after a Choice is rolled after the player chose. This is what the bytecode already does
when an expression is written after an `await`, so the generator needs no copies.

A value from before the split is read again after it, not carried over. The cases that would need carrying (the
`other` actor, input, physics) are the ones the table forbids, so nothing silently changes meaning. If a later
version wants "remember this value", it becomes an explicit node that stores into a `Game` field.

## Running next to the game (P20.02)

Running every graph chain as a cutscene would freeze the player for a coin that waits one second before it plays a
sound. So the chain picks its priority from what it contains:

- **Contains Say, Choice or Move:** a cutscene, as today: the player stops, input is ignored, the pause menu waits,
  and Save during cutscenes keeps it (P20.06).
- **Only Wait, Fade and instant nodes:** runs beside the game at `Priority::Trigger`. Input, physics and the player
  keep going; it is not stored in a save (on load it is simply not running).

In C#: `[Cutscene]` keeps its meaning, and `[Cutscene(Background = true)]` starts at `Trigger`. The generator writes
`Background = true` for chains of the second kind; hand-written cutscenes can use it too.

**One run at a time per actor.** `OnTouch` fires every frame and a button can be pressed again while the chain still
waits. A `...Waits` method does not start again while its previous run for the same actor is still going; the new
call does nothing. In C# this is `[Cutscene(Once = true)]`, which the generator always writes; the VM checks script
id plus actor index in `start`. Without it, standing next to the shopkeeper would fill all 8 contexts in 8 frames.

## Limits the user can hit

- 8 scripts running at once in the whole game (VM contexts). The 9th does not start and the Console says so once.
- 16 variables per waiting chain: each Choice uses one. The build error names the cutscene (`OnTouchWaits`).
- Nodes after the split cost bytecode time instead of C++ time. Dialogue-sized chains are far below a frame; a chain
  with hundreds of nodes after a wait is the case to measure in P20.04's ROM test.

## What was built (2026-11-07)

- `[Cutscene(Background, Once)]` (`tools/AgbStudio.Api/Behaviour.cs`), `agb_start_script_as` in the generated
  prelude, and `script::start(..., once)` in the VM, which keeps the script a context started with and its once key.
- A cutscene resumed from a save does not know which actor started it, so while it runs a `Once` start of the same
  script is refused for every actor (`kOnceAny`). Otherwise the actor's On Start would start a second copy beside it.
- `GraphCodeGen` and `GraphFromCode` for the six nodes, `GraphChecks` for P20.05, the Choice rows in the editor.
- **Not usable yet: Move.** No build fills `ScriptCompileContext.Paths` (only tests do), so a real project has no
  path names and `await Move(actor, "x")` fails to build with an unknown path. Paths need the Scene Editor to draw
  them and the build to export them; until then the Move node is in the palette but can't be used in a game, and
  P20.06 is tested for Say only.

## Questions for the owner

1. **Priority from contents:** chains with Say / Choice / Move freeze the player, chains with only Wait / Fade run
   beside the game. Recommended. The other choice is "always freeze", which is simpler but makes timed effects stop
   the player.
2. **One run per actor, always on for graphs.** Recommended. The other choice is a checkbox on the event node.
3. **The C# spelling** `[Cutscene(Background = true, Once = true)]` for hand-written scripts too. Recommended, since
   graph code and hand-written code then use one rule.
4. **Move's actor:** Self (the graph's actor) or Player, chosen on the node, since bytecode cannot hold another actor.
   Recommended; other actors need a way for bytecode to hold an actor, which no phase plans yet.
